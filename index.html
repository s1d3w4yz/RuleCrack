Password Cracking Rule Chain Lab

Password-cracking tools like hashcat and John the Ripper don’t only try words from a list: they can also be told to apply rules to each word — capitalize it, add a 1 at the end, swap a for @ — to guess the variations people really use. A rule is a chain of small steps run in order. Build one below, watch each step fire, and see how reordering, adding or removing a step changes the result. Positions count from 0, in bytes (é is 2 bytes). Use this only on systems you are authorized to test.

  • Hashcat syntax default Unambiguous and the de facto standard. Most published rule lists use it, and John the Ripper can run it in its hashcat-compat mode, so it's portable.
  • John's native syntax special cases Only when hashcat can't express what you need, like pluralization or John's own character classes.

Paste a .rule file (or a John List.Rules section) and check every line against a real parser, not a guess. Fix a broken line inline or in the chain builder, delete what you don't want, then export the cleaned file.

  • Blank lines and comments kept Blank lines and # comments pass through untouched.

hashcat ↔ John native compatibility

Of the 56 operators shared between hashcat and John's own native syntax, which actually behave identically with no !! hashcat logic ON wrapper at all — not just which parse the same way.

Method

A rule only counts as compatible here if the literal text is valid in both dialects and gives byte-identical output. Boundary-aware testing — word lengths 0, 1, 2, 5, 8 and each operator's own position argument at 0, length−1, length, length+1, length+2, plus named positions 9/10/35 — comparing this tool's hashcat engine against its John-native engine, both independently verified against real binaries: hashcat v7.1.2-850-gb3ecf3293 (4,800/4,800 checks agreed with the installed v7.1.2) and John 1.9.0-jumbo-1+bleeding-302f52709 (every divergence below re-confirmed directly against this binary).

A step that empties the word: hashcat keeps it, John native rejects it

[ delete_first] delete_lastD delete_at' truncate_atO omitx extract

John's native engine re-checks "did the word just become empty?" after every step (src/rules.c:1755) and rejects the candidate if so — hashcat's engine has no equivalent. Any op that can reduce a word to zero length trips it.

Length-reject boundary is off by one

< reject_less> reject_greater

hashcat's <N keeps a word when length ≤ N; John's native <N only keeps it when length < N (symmetric for >). At exactly length == N the two disagree.

Memory ops default differently before any "M"

4 append_memory6 prepend_memoryQ reject_memoryX extract_memory

hashcat treats the saved-word buffer as unset until M runs, and rejects anything that uses it before then. John's native engine initializes it to a copy of the original word, so these all work immediately.

Insert past the end of the word

i insert

hashcat's kernel leaves the word unchanged when the insert position is out of range. John's native engine appends the character at the end instead, whenever the position is ≥ the word's length.

rulei2aword"x" (len 1) hashcat"x" (no-op)John native"xa"
verified against real john + hashcat binaries

A letter or "8" position code after "-" reads as a reject flag

- chr_decr

John's native parser treats a leading - followed by anything other than a digit 0–9 (and specifically excludes 8 too) as one of its own line-level reject flags, not the decrement-byte command. So -A through -Z (positions 10–35) and -8 fail as a syntax error in native mode instead. Plain digits (-0–-9, except -8) are unaffected.

Scope and limits

The word space either engine can receive is effectively infinite, so nothing here is a proof that the 42 compatible operators always agree — it's boundary-focused differential testing, not exhaustive verification, and no realistic amount of testing closes that gap completely.

  • Each operator was tested alone, not chained with others. A multi-step rule combining two "compatible" operators should stay compatible — nothing found suggests an interaction effect — but that's an inference from each step's isolated behavior, not something directly tested.
  • Character arguments were tested with a representative set (a, Z, !, space, 0), not the full byte range — null bytes, 0xFF and other extreme values weren't specifically stressed.
  • Position/length boundaries were tested at word lengths up to 8; the separate check that found and fixed a 320-byte length bug didn't also cross it with boundary-position testing at large lengths.

Treat the 42 compatible operators as reliable for ordinary passwords and ordinary rules — what this tool is for — not as a mathematical guarantee for every conceivable input.
